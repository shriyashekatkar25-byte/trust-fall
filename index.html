The decision

the customer.

Customer problem

A data platform team running hundreds of jobs gets a background agent that finds the broken pipeline, names the root cause, and drafts the fix. Then the fix waits for a human. At 2am, the waiting is the outage.

Many of these fixes are boring: a retry after an upstream blip, a new nullable column from schema drift. Reviewers approve them in seconds, but only after they wake up.

↳ “treasure” = a fix nobody had to read.
the change.

Proposed change

An opt-in, admin-controlled “earned lane”: a fix category that has proven itself in human-reviewed history may open, sandbox-test and merge its own pull request, with one-click revert and a notification. Everything else stays in today's review queue.

A category graduates only when the posterior says P(success rate ≥ bar) ≥ confidence. It's demoted when the evidence slips.

north star.

Success metric

Median time-to-recovery for broken jobs and pipelines in opted-in workspaces, target −40% versus the review-only control in 8 weeks.

Secondary: reviewer hours saved per workspace per week.

guardrails.

what's true today.

Grounding

Per the public docs, the agent today proposes fixes and never changes production data or code without human review. This prototype asks a narrower, hypothetical question: if we ever relaxed that, where would the evidence support it, and where never.

WHAT I'D TELL THE VP IN ONE SENTENCE

The math, from my Monte Carlo course

Frequentist vs Bayesian. A frequentist would say each fix category has one fixed success rate and report its sample proportion (the MLE), maybe with a confidence interval. A Bayesian treats the unknown rate as something we have beliefs about, and updates those beliefs as reviewed fixes come in. For a launch gate, the Bayesian question is the useful one: given what we've seen, how likely is it that this category is actually good enough?

Beta prior + Binomial data = Beta posterior. If my belief about a rate is Beta(a, b) and I then watch n fixes with k clean ones, my updated belief is Beta(a + k, b + n − k). No integrals needed; the counts just add on. That's conjugacy.

Posterior mean is a weighted average. The prior here is centered on the pooled rate across all categories. A small category gets pulled toward that pooled rate; a big one mostly speaks for itself. That shrinkage is what keeps a lucky 20-for-20 category from graduating on day three. Set prior strength to 0 and the prior is flat, so the posterior peak (MAP) equals the plain sample rate (MLE).

posterior = Beta(a + k, b + n − k) mean = w·(prior mean) + (1−w)·(k/n) w = (a+b)/(a+b+n) P(p ≥ bar) ≈ (1/M) Σ 1{ p⁽ᵐ⁾ ≥ bar }

Where Monte Carlo comes in. Instead of computing the Beta tail exactly, I draw M = 4,000 samples from each posterior and count the fraction above the bar. Each draw is built from two Gamma draws (Beta = X / (X + Y)), and those use normal draws, so it's sampling stacked on sampling. The same draws give the 90% credible interval (5th and 95th percentile of the samples) and the distribution of net hours saved, which is the number a VP actually cares about.

Credible vs confidence. “There's a 93% chance this category's true rate is above 97%” is a credible-interval statement about this parameter, given this data. A confidence interval only promises coverage over repeated experiments, before you see the data. Execs hear the first one correctly.

Break-even bar. With 0.6 h saved per good fix and C hours lost per bad one, auto-merge pays off only if p > C / (C + 0.6). At C = 8 that's about 93%, which is why the default bar sits above it.

How I'd run it on real data

Illustrative schema: one row per agent-proposed fix, with the human review outcome and whether the job stayed healthy for 24 hours after.

-- 1. Clean-fix counts per category, last 12 weeks (illustrative tables)
CREATE OR REPLACE VIEW ops_lab.fix_track_record AS
SELECT
  f.fix_category,
  COUNT(*)                                                     AS reviewed,
  COUNT_IF(r.decision = 'approved' AND h.healthy_24h)           AS clean,
  COUNT_IF(f.touches_data_rows)                                  AS data_touching
FROM ops_lab.agent_fixes f
JOIN ops_lab.fix_reviews   r USING (fix_id)
JOIN ops_lab.job_health_24h h USING (fix_id)
WHERE f.proposed_at >= current_date() - INTERVAL 84 DAYS
GROUP BY f.fix_category;
# 2. Posterior gate per category (runs in a notebook or scheduled job)
import numpy as np
rng = np.random.default_rng(20261114)
df  = spark.table("ops_lab.fix_track_record").toPandas()

BAR, CONF, STRENGTH = 0.97, 0.90, 60
pooled = df.clean.sum() / df.reviewed.sum()
a0, b0 = STRENGTH * pooled, STRENGTH * (1 - pooled)

def gate(row, m=4000):
    draws = rng.beta(a0 + row.clean, b0 + row.reviewed - row.clean, m)
    return (draws >= BAR).mean(), np.quantile(draws, [.05, .95])

df[["p_clear", "ci90"]] = df.apply(gate, axis=1, result_type="expand")
df["lane"] = np.where((df.p_clear >= CONF) & (df.data_touching == 0),
                      "earned", "review")
spark.createDataFrame(df).write.mode("overwrite").saveAsTable("ops_lab.lane_status")

I'd rerun the gate weekly, alert when a category's P(≥ bar) drops below the demotion line, and log every lane change to an audit table governed in the catalog.
